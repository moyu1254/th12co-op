# 実ゲームテストの無音・非干渉実行

自動テストは専用コピーを停止状態で作成し、ゲームの最初の命令を実行する前にテスト専用の出力制御DLLを導入する。ゲームのウィンドウは不可視かつ `WS_EX_NOACTIVATE` に固定する。マウス・キーボードの入力送信、クリップボード操作、ユーザーのフォーカスを戻す操作は行わない。

`build.ps1 -SmokeTest` で `th12coop-quiet-test.dll` を別途ビルドする。`injector --early --quiet-test` は既知のEXEの停止境界でこのDLLを先に読み込み、成功してから通常またはsmoke DLLを読み込む。DLLは必要な全インポートを検査してから成功を返す。ハーネスは導入に失敗した場合ゲームを再開せず終了する。

既知のEXEハッシュとエントリーポイントの5バイトを照合してから、起動時の停止処理を設置する。エントリーポイントを一時的に専用RXページへ分岐し、レジスタ・フラグ・スタックを変更しない `mov [ready],1; jmp self` を実行する。`ready` は別のRWページ上に置く。

親プロセスは到達通知を読んでからスレッドを停止し、`GetThreadContext` で停止完了と待機ループの命令位置を確認する。確認に成功した場合だけエントリーポイントの5バイトとEIPを戻し、一時ページを解放する。タイムアウトや取得失敗では停止用の処理を残したまま所有プロセスを終了する。`SuspendThread` の成功だけでは停止完了の証拠としない（[Microsoftの解説](https://devblogs.microsoft.com/oldnewthing/20150205-00/?p=44743)）。

この方式は、旧方式が入口到達前に `GetThreadContext` を反復し、初回にエラー31を返した実測を受けて導入した。WOW64の初期化中にx86コンテキストが未準備だった可能性はあるが、エラー31の原因がそれに限定されるとは確認していない。実際の入口到達を通知することで、途中のコンテキストが取得できるという前提を除去した。旧失敗記録を残し、変更後は3版各30回、計90回の停止状態での初期化を確認した。

ウィンドウ生成・表示・位置・styleの変更を制限し、フォアグラウンド化、ダイアログ、カーソル表示・形状、キーボード状態、IME状態、システム設定変更、ゲーム本体からの子プロセス起動を抑止する。`SendMessageA(WM_SYSCOMMAND)` による最小化・復元も抑止し、`GetProcAddress` で動的取得する `MessageBoxA` にも同じ制御を適用する。OSのエラーダイアログはプロセス単位の `SetErrorMode` / `WerSetFlags` で禁止する。`ShowCursor` は原作の反復条件が終了する戻り値を返し、実際のカーソルカウントを変更しない。Direct3Dのデバイス生成はwindowedのみ許可し、[`D3DCREATE_NOWINDOWCHANGES`](https://learn.microsoft.com/en-us/windows/win32/direct3d9/d3dcreate) によりランタイム側のフォーカス変更も禁止する。

このDLLはTH12がインポートする `DSOUND.dll` ordinal 11 (`DirectSoundCreate8`) をラップする。副バッファに音量制御を付け、作成時・音量変更時・各 `Play` 呼出しの直前に [`DSBVOLUME_MIN`](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee418150(v=vs.85)) (-10000) を設定する。無音化に失敗したバッファは再生しない。音声の再生位置や時計は原APIへ委譲し、無音の副バッファだけをバックグラウンドで進める。

ストリーミング再生の `IDirectSoundNotify` も所有バッファを保持するラッパーで提供し、通知位置の登録を原APIへ委譲する。初期版のテスト制御DLLはこのinterfaceを提供せず、BGMの初期化不成立からpause時に失敗した。通知を保持した最終版で3版のpause/resumeを再検証した。この失敗はテスト制御側の不備として記録し、製品DLLの成功結果に混在させない。

他のアプリに影響し得るプライマリバッファの音量・形式・再生・停止は変更しない。プライマリバッファの書込みは拒否し、協調レベルを `DSSCL_NORMAL` に限定する。スピーカー構成の変更も無効化する。Windowsのマスター音量、出力デバイス、他プロセスの音声セッションは操作しない。各PCの音量設定が異なる試験も行えるよう、無音化を設定ファイルの音量0だけに依存させない。

`Local\TH12CoopQuiet_<pid>` の読取専用観測で、音声デバイス・バッファ・無音再生・失敗の回数を確認できる。ゲームを初期化してもデバイス数が0の試験は、音声経路を実行した検証とは扱わない。

Pythonの `QuietEnvironment` とランチャーの `OwnedGameJob` は起動したゲームだけを終了管理に登録する。登録はプロセスを再開する前に行い、ハーネスが異常終了してもJobハンドルの破棄でゲームを終了させる。通常終了でも対象のプロセスハンドルで終了を確認してからハンドルを閉じる。既に稼働しているSteamや他アプリは終了しない。injectorなどの補助コマンドはウィンドウを表示しない。

## 検証範囲と制約

- x86 `QUIET_GUARD_SELF_TEST` は実際のラッパーを偽の音声バッファに接続し、プライマリへの変更が0回、副バッファが再生直前に無音になること、無音化失敗時に再生しないことを確認する。不可視の小さな所有ウィンドウで表示・style変更・activationの抑止も確認する。音声デバイスやゲームは起動しない。
- 非表示のゲームは最小化しない。最小化によるDirect3Dの停止と、入力・同期の不具合を区別するため。
- 初期調査で非入力の専用デスクトップを試したが、通常1.00aは音声の無音化後、Direct3D初期化で120秒待機したため所有プロセスを終了した。この経路は実ゲームの成功結果に含めない。最終の方式では使用中のデスクトップ上に不可視・非activationのHWNDを作り、ゲームおよびDirect3Dのウィンドウ変更経路を制限する。デスクトップの切替・フォーカス復元は行わない。
- 音声経路の制御があるため、可聴音質、通常の協調レベル、フォアグラウンド操作感、表示の目視品質はこの方式では検証できない。これらと別PC/WANの確認は個別に扱う。
- `th12coop-quiet-test.dll` とsmoke DLLは配布ZIPから除外し、`verify_package.py` も診断DLLの混入を拒否する。通常の製品DLLにはこの音声制御を含めない。
