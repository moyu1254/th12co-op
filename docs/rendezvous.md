# 部屋番号で接続する（開発版・Phase 1）

両者が同じ合流サーバーを選べば、毎回伝えるのは6桁の番号だけです。サーバーはホストへの接続先と招待を一度だけ渡し、その後の操作入力やゲーム資産は受け取りません。ゲームの通信はホストとゲストの間の直接 TCP/TLS です。

## ランチャーの設定

運用者から信頼できる経路で HTTPS の接続先を取得し、両方の PC の環境変数 `TH12COOP_RENDEZVOUS_URL` に設定してからランチャーを起動します。値はドメイン名とポートまでで、パス・ユーザー名・クエリは指定できません。OS が信頼し、この名前に対して有効な証明書が必要です。以下は PowerShell でその起動だけに設定する例です。`rooms.example.org` は運用者の実際のホスト名に置き換えてください。

```powershell
$env:TH12COOP_RENDEZVOUS_URL = 'https://rooms.example.org:8443'
.\Start.cmd
```

番号による[作成・参加の手順](../README.md#オンライン)を実行します。ホストのルーターがUPnPを提供しない場合はTCP 3012を手動転送するか、直接接続でLAN・VPNを使ってください。ランチャーはWindowsファイアウォールの設定を変更しません。

## サーバーを運用する

Phase 1は、小規模グループの運用者が既存ホストで動かす単一プロセスの ASP.NET Core 10 / Kestrel を採用します。公式サービス・クラウド契約・従量課金はなく、このプロジェクトのホスティング費用枠は0円です。運用者が証明書の取得と更新、OS/.NETのパッチ、アクセス制限、既存回線の費用を管理します。複数インスタンスで部屋は共有しません。

1. TLS 1.3 に対応するホストと .NET 10 SDK を用意します。接続名に対するサーバー証明書・秘密鍵・必要な中間証明書を PFX として用意し、サービス用アカウントだけに読み取りを許可します。
2. `dotnet publish src/rendezvous -c Release -o build/rendezvous` を実行します。実行先には ASP.NET Core 10 ランタイムが必要です。原作とランチャーは不要です。
3. `TH12_RENDEZVOUS_PFX` を PFX の絶対パスに設定し、必要なら `TH12_RENDEZVOUS_PFX_PASSWORD` をサービスのシークレット設定から渡します。`TH12_RENDEZVOUS_PORT` は未設定なら8443です。`dotnet build/rendezvous/TH12Coop.Rendezvous.dll` で起動し、指定した TCP ポートを両者から到達可能にします。秘密鍵・パスワードはリポジトリに保存しません。
4. [Kestrel](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0)が直接 HTTPS を終端し、ソケットの接続元をゲームの候補にします。TLS を終端するリバースプロキシ、CDN、転送元ヘッダーには対応しません。本文・IP・番号を収集するアクセスログ、プロキシ解析、APM、メモリダンプを有効にしないでください。

番号方式で渡す候補は登録時に観測した IP 一つと固定の TCP 3012 です。IPv4 UPnP の転送を使う運用では IPv4 の接続先を用意します。ホストが IPv6 で登録すると IPv6 を持たないゲストは到達できません。番号方式はサーバー指定のLAN内アドレスを受理しません（ローカル試験でのループバックを除く）。両者が同じNAT内で外側アドレスに戻れない場合も、LANの直接接続を選んでください。

## HTTP インターフェースと保持期間

すべて固定パスへの HTTPS POST、JSON の本文のみを使います。秘密を URL に入れません。リスト、ゲームデータ転送、任意宛先の中継、永続ストレージはありません。

| パス | 送る値 | 成功時 |
|---|---|---|
| `/v1/rooms/create` | `invite`, `port`（3012） | 200: `number`（先頭ゼロを含む6桁文字列）、`ownerToken`（256-bit） |
| `/v1/rooms/join` | `number` | 200: `invite`, `address`, `port`。同時の問い合わせでも取得できるのは1件 |
| `/v1/rooms/close` | `number`, `ownerToken` | 204: 所有者だけが取消可能。使用済み・不在・権限不一致も同じ応答 |

作成から10分で期限切れ。取得・取消時には招待、候補、取消鍵を部屋一覧から外し、番号だけを元の有効期間の終わりまで予約します。取得後に接続が失敗しても同じ番号は再利用できません。全32枠が予約中なら503、不在・取得済み・失効への問い合わせは404です。プロセス再起動で全室が失効し、使用済み番号の予約も消えます。メモリ内の文字列や OS のページファイルの物理消去は保証しません。

操作ごとに、直近10分間に受け付ける要求数を制限します。該当する上限のいずれかに達すると、その要求には429を返します。

| 集計範囲 | 作成 | 参加 | 取消 |
|---|---:|---:|---:|
| IPv4 アドレスまたは IPv6 /64 | 4 | 6 | 12 |
| IPv6 /56 | 8 | 12 | 24 |
| IPv6 /48 | 12 | 24 | 36 |
| サーバー全体 | 48 | 120 | 96 |

IPv6 では同じ /48・/56 に属する利用者でそれぞれの枠を共有します。頻度制限で拒否した要求は他の枠を消費しません。集計用に保持するのは、受付時刻と送信元（IPv6は /64 まで）の最大264件分です。

最大同時64接続・本文512 bytes、TLSハンドシェイク・要求本文ともに5秒が上限です。接続元と部屋情報のアプリログは保存しません。複数の割り当て元からの負荷で全体上限に達した場合や、回線そのものが混雑した場合は、正規の利用者も接続できないことがあります。
