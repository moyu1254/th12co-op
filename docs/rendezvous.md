# 部屋番号で接続する（開発版・Phase 3）

ホストとゲストは同じ合流サーバーを選び、6桁の番号で合流します。ゲストの参加時に両者が UDP の接続候補を交換し、ICE の接続性チェックで選んだ経路に直接 QUIC/TLS 1.3 を張ります。直接経路を確立できないときは、同じ番号のまま WSS 中継へ移ります。ゲームを始める前に両方の画面の照合コードを別経路で確認してください。[オンラインの手順](../README.md#オンライン)・[通信ガイド](network-security-design.md)も参照してください。

## ランチャーの設定

運用者から信頼できる経路で HTTPS の接続先を取得し、両方の PC で `TH12COOP_RENDEZVOUS_URL` を設定してから起動します。ドメイン名と任意のポートまでを指定します。OS が信頼し、その名前に対して有効な証明書が必要です。以下の `rooms.example.org` は運用者のホスト名に置き換えてください。

```powershell
$env:TH12COOP_RENDEZVOUS_URL = 'https://rooms.example.org:8443'
.\Start.cmd
```

ホストは番号を発行して待ちます。ゲストが番号を入力すると、STUN で集めた候補を登録し、招待と受取用の鍵を取得します。ホストはこの時点で自分の候補を集めて応答します。IPv4 のホストでは UPnP で UDP のポート転送も試みます。Windows ファイアウォールの許可は利用者が設定します。

中継にも同じ HTTPS ホスト・TCP ポートを使います。ゲーム通信はその内側で相手と暗号化します。いずれかの端末から WSS が使えない場合や中継が満杯の場合は、番号方式での接続は成立しません。LAN・VPN などでは手入力の直接 TCP 接続も選べます。[接続試験の範囲](../verification/phase3-relay.md)

## サーバーを運用する

この構成は小規模グループ向けです。運用者が DNS、証明書、OS/.NET と STUN サービスの更新、回線・費用上限、アクセス制限を管理します。プロジェクト提供の公開サービス・クラウド契約はなく、プロジェクトのホスティング費用枠は0円です。

1. TLS 1.3 対応ホストに .NET 10 SDK を用意し、`dotnet publish src/rendezvous -c Release -o build/rendezvous` で HTTPS サーバーをビルドします。実行先に ASP.NET Core 10 ランタイムが必要です。
2. 接続名に対するサーバー証明書・秘密鍵・必要な中間証明書を PFX にまとめ、サービス用アカウントだけが読める場所に配置します。`TH12_RENDEZVOUS_PFX` に絶対パスを指定し、必要に応じて `TH12_RENDEZVOUS_PFX_PASSWORD` をサービスのシークレット設定から渡します。`dotnet build/rendezvous/TH12Coop.Rendezvous.dll` で起動します。HTTPS は既定で TCP 8443 です。`TH12_RENDEZVOUS_PORT` で変更できます。
3. 同じ DNS 名の UDP 3478 に STUN Binding サービスを別途用意します。例えば coturn では `stun-only` モードを使い、使用するアドレスで UDP を受け付けます。IPv6 と IPv4 の両方を提供する場合は AAAA・A を設定し、HTTPS と STUN の双方が各ファミリーで到達可能になるようにします。HTTPS サーバーのプロセスは STUN を提供しません。[coturn の設定例](https://github.com/coturn/coturn/blob/master/examples/etc/turnserver.conf)・[STUN の仕様](https://www.rfc-editor.org/rfc/rfc8489)。
4. Kestrel が直接 HTTPS を終端します。TLS 終端プロキシや CDN を置くと候補の送信元を証明できません。部屋・IP 証明・WSS 中継は単一プロセスで管理します。HTTPS・WSS・STUN のすべてで本文・認証ヘッダー・番号・接続元のアクセスログ、APM、ダンプの保存を無効にし、STUN にも運用環境側の受信・帯域制限を設定してください。[Kestrel のエンドポイント](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0)。

各端末は、候補がある IP バージョンごとに HTTPS 接続を張り、そのソケットの接続元 IP に対する短期の証明トークンを取得します。サーバーがそのトークンで確認したアドレスだけを相手に渡します。STUN と HTTPS の出口 IP が異なる候補は登録できません。DNS 名・LAN 内・リンクローカル・予約済みの宛先は受理しません。ループバックの HTTPS を明示設定するローカル試験は例外です。証明対象は IP で、UDP ポートは ICE で実際の到達性を検査します。

## HTTP インターフェースと保持期間

次の固定パスへ JSON を HTTPS POST します。応答には `Cache-Control: no-store` を付けます。これらの POST の招待・ICE パスワード・トークンは本文にのみ含めます。直接接続に成功すればゲーム通信はサーバーを通りません。中継時もゲーム資産は扱いません。

| `/v3/rooms/` の下のパス | 送る値 | 成功時 |
|---|---|---|
| `create` | `invite`（T12L7） | 200、`number`（6桁）、`ownerToken` |
| `proof` | 空のオブジェクト | 200、観測した `address` と `token` |
| `join` | `number`, `offer`（証明付き候補） | 200、`invite`, `guestToken`。番号を消費 |
| `offer` | `number`, `ownerToken` | 200、ゲストの候補。応答の発行前は同じ所有者が再取得できる |
| `answer` | `number`, `ownerToken`, `ice`（証明付き候補） | 204、ホストの候補を発行。同じ候補での再送も204 |
| `receive` | `number`, `guestToken` | 200、ホストの候補。同じゲストが保持期限まで再取得できる |
| `close` | `number`, `ownerToken` | 204、所有者が取り消す。不在・権限不一致も同じ応答 |

証明付き候補は `description` と `proofs` から成ります。`description` の項目は `ufrag`（4～256文字）、`password`（22～256文字）、`candidates`（1～4件）です。候補は数値 IP の `address` と UDP の `port`（1024～65535）だけを持ちます。`proofs` は IPv4・IPv6 の証明トークンを最大2件含み、相手には渡しません。候補がないときだけ、空文字の `ufrag`・`password` と空配列の `candidates`・`proofs` で通知します。確認できなかった候補を証明なしで渡すことはできません。所有者用・ゲスト用・IP 証明トークンはそれぞれ独立した256-bitの乱数です。

部屋の期限は作成要求の受付から10分です。参加を受け付けた時点で番号を消費し、招待を部屋から外します。候補を返した HTTP 応答が届かなくても、同じ役割のトークンで再取得できます。ホストが `answer` を発行するとゲストの候補を消去します。以後ホストの候補は発行から90秒または部屋の期限の早い方まで保持し、同じ内容の再送だけを受理します。候補の再取得・再送で期限は延びません。取消・失効時には両者の権限と候補を破棄し、番号だけを元の期限まで予約します。IP 証明と頻度制限の受付記録は各受付から10分で失効します。プロセス再起動でメモリ内の予約・証明は失効します。OS のページファイルなどの物理消去は保証しません。

各部屋で役割ごとに1件だけ候補の到着を待ちます。1回の待機は `offer` が最大20秒、`receive` が最大2秒です。期限までに候補が届かなければ204、部屋・権限が無効な場合は404を返します。Kestrel の64接続のうち、候補待ちが使用できるのは全室で最大48枠です。認証済みの問い合わせは、同じ役割がすでに待機中なら即時204、新たな待機が必要で全枠が使用中なら503を返します。すでに届いている候補は待機枠が満杯でも取得できます。ポーリング後は HTTP 接続を閉じ、作成・参加・IP 証明に枠を使えるようにします。

ランチャーは204の後は250 ms、503の後は1秒待って同じ資格情報で再取得します。応答が途中で切れた場合は、1回の問い合わせあたり最大3回再送します。`create` と `join` は自動再送しません。

次の値は操作ごとの直近10分の受付件数です。上限に達した送信元または操作は本文を読む前に429を返します。`offer` と `receive` では、新しい待機の開始、保存済み候補の取得、不正な資格情報や本文を各1回と数えます。待機を開始した要求は、期限切れや切断でも1回分を使います。同じ役割が待機中の即時204と、待機枠不足の503は、いずれも再試行時の受付件数に加算しません。

| 集計範囲 | create | join | proof | offer | answer | receive | close |
|---|---:|---:|---:|---:|---:|---:|---:|
| IPv4 アドレスまたは IPv6 /64 | 4 | 6 | 24 | 160 | 12 | 320 | 12 |
| IPv6 /56 | 8 | 12 | 48 | 320 | 24 | 640 | 24 |
| IPv6 /48 | 12 | 24 | 72 | 480 | 36 | 1280 | 36 |
| サーバー全体 | 48 | 120 | 384 | 1920 | 96 | 3200 | 96 |

Kestrel の通常 HTTP は最大64接続、本文4096 bytes、TLS ハンドシェイクと要求本文の受信は各5秒です。多数の送信元による利用枠の消費や回線混雑によって、期限内でも接続に失敗することがあります。

## WSS 中継

両者とも運用者の同じ TLS 1.3 エンドポイントへ HTTP/1.1 の WebSocket upgrade を要求します。ホストは `GET /v3/relay/host`、ゲストは `GET /v3/relay/guest` を使い、`X-TH12-Room` に部屋番号、`Authorization: Bearer` に自分の役割のトークンを入れます。URL に番号、鍵、転送先を指定する処理はありません。ホストが応答を発行してから候補の保持期限までに両者が到着すると、同じ部屋を1回だけペアにします。成立済みの中継は候補の保持期限とは独立して動きます。

| 上限 | 値 |
|---|---|
| サーバー全体 | 片側待ちを含めて8組。upgrade 後は最大16接続 |
| 片側の到着待ち／双方の upgrade | 最大35秒／5秒 |
| ペア成立後 | 最大2時間、転送量は双方向の合計で64 MiB（内側の TLS を含む WebSocket ペイロード） |
| メッセージ | バイナリのみ。断片合計16 KiBまで、圧縮なし。片方向ごとに1メッセージを処理 |
| upgrade 試行数／10分 | IPv4 アドレスまたは IPv6 /64 で24件、/56 で48件、/48 で72件、全体で192件 |

不正な役割や再使用は404、満室は503、試行過多は429です。片側の待機期限に達すると要求は408または切断で終了します。片側の切断、転送失敗、上限到達で両方を閉じます。各部屋の上限は回線費用の月額上限ではありません。運用者はホスティング側の帯域・課金上限を別に設定し、ヘッダー・通信内容を記録しないでください。
