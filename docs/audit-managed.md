# ランチャーの準備・通信・停止処理の監査

対象は `400c4b7` からの管理側の修正。既知のゲーム資産、TLS証明書pin、参加鍵、入力の許可bit、連続frame、保存件数・通信頻度の制限を維持した。協力ルールはnative側の変更に合わせて3とし、通信版3・IPC構造体版1は変更していない。

## 再現した問題と修正

| ID | 再現条件・以前の結果 | 修正 |
|---|---|---|
| M1 | キャンセル済みtokenでSteam用App IDを新規作成すると、空の最終ファイルが残り、再試行が拒否された。初期`th12.cfg`の作成も同じ「最終名を作ってからキャンセル可能な書込み」を使用していた。 | `GameConfiguration.WriteNew`で同じディレクトリの一時ファイルへ書込み・flushを行い、完了後だけ最終名へ移動する。失敗時は一時ファイルを削除し、既存ファイルは上書きしない。設定テンプレートのサイズとmagicも検証する。 |
| M2 | セッション準備の中止や資産読取り失敗で、部分的な`host`フォルダーが残った。 | 一意の一時フォルダーで全資産・設定の準備と照合を完了し、最後にセッションの最終フォルダーへ移動する。中止・失敗時には今回の一時フォルダーだけを回収する。 |
| M3 | manifest作成後に依存DLLやnative DLLを変更しても、古いhashの合意のままセッションを準備できた。 | 実際に準備したEXE/DAT/BGM・許可された依存DLL・設定と、実際に注入する`NativePath`を再hashし、合意時の値と一致しなければ公開しない。 |
| M4 | 接続相手が既に切断していても、開始・ready待機より前の準備が進み、セッションフォルダーが公開された。 | 受信Taskの終了を準備・起動処理のlifetimeへ即座に反映する。派生したキャンセルが元の通信例外を隠さないよう、元の例外を保持する。起動前pingの通信失敗も同じ停止へ接続する。 |
| M5 | 実際のTLS受信40秒期限が、利用者の中止と同じ`OperationCanceledException`になった。 | 内部の接続10秒・認証4秒・送信5秒・受信40秒期限は`TimeoutException`として理由を表示する。利用者からのキャンセルは引き続き`OperationCanceledException`とする。 |
| M6 | `Abort(3)`の後で通常の後始末が`Abort()`を呼ぶと、同期不一致の理由が1へ上書きされた。 | 最初のabort理由を保持する。abortの書込みとDisposeを同じ排他区間で管理する。 |
| M7 | ローカルIPCに未対応bitを置くと`LocalInput`が受理し、Pumpが無言でmaskしていた。 | native側が物理入力をプロトコル用の`0x1FB`へ変換してから公開し、管理側はIPCの未対応bitを拒否する。原作コントローラー処理には`0x200`を返す正規経路があるため、物理入力そのものを不正と扱わない。nativeの変換はSmoke family5/case7、IPC破損は管理側の試験で分けて検証する。 |
| M8 | 診断先フォルダーがないと、同期不一致のログ書込みがabortより先に失敗し、後始末のtail保存も元の中止例外を隠した。 | 不一致はまず固定サイズの値として保持し、ただちにabortする。所有ゲームとTaskの後始末後にだけ診断を保存する。各保存は500msのキャンセル期限を持ち、I/O・権限・保存キャンセルの例外は元の停止理由を置き換えない。 |

`ConfigurationSnapshot`の既存の復元経路は、破損した起動後ファイルを元の有効な60byteへ完全復元する試験と、初回起動が作った新しい不正ファイルを削除する試験に合格した。既存のユーザー設定が不正な場合は引き続き起動を拒否し、自動的に設定を捨てない。

`OnlineProfile.NativePath`は`GameSession.Start`へ明示的に渡され、同じパスがinjectorの引数になる。再照合は接続待ち中の更新によるmanifestの陳腐化を検出するものであり、照合後に同一ユーザーの別プロセスがファイルを差し替えることまで防ぐ仕組みではない。

## 回帰試験

新規の`ManagedAuditTests.cs`は、一時領域内の小さな合成ファイル、実際のWindows共有メモリ、ループバックのTLS 1.3を使用する。ゲームファイルの識別だけを合成fixtureで置き換え、準備・入力検証・通信・終了の実装そのものを呼ぶ。原作のゲーム資産・native DLLの読込み・ゲームプロセスの起動は行わない。

修正前に保存した結果:

- 初回の10グループでは8グループが失敗。設定作成、部分的な準備、古いmanifest、入力bit、準備中の切断、実際の40秒期限を確認した。
- 追加したabort理由保持の試験は、初期修正後の12グループ中で唯一失敗し、その後に修正した。
- 診断先を消した2グループは両方失敗し、その後にM8を修正した。

通常の`--self-test`には、従来の11グループに加えてこの監査suiteを1グループとして組み込んでいる。監査suiteは16グループで、接続・認証・送信・受信には本番の時間制限を使う。送信期限は、受信しない相手に対する実際のTCP backpressureで確認する。テスト全体の120秒期限はテスト用であり、実際の通信期限を緩和しない。

分離出力`build/managed-audit/out`での修正後の完全な`--self-test`は終了コード0、12グループ合格、内包する監査suiteも16/16合格だった。ビルドは警告0・エラー0。`build/managed-audit/verification.json`に試験したsource・assemblyのSHA-256と、現在のsourceが試験時のコピーと一致することを記録した。配布用ビルドの結果は別途releaseの検証記録を正とする。

```powershell
dotnet TH12Coop.dll --self-test
# 監査suiteだけ、または診断出力失敗だけを再現する場合
dotnet TH12Coop.dll --managed-audit-test
dotnet TH12Coop.dll --managed-audit-test --audit-filter Diagnostic
```

結果は実行したランチャーと同じフォルダーの`launcher-test-results.txt`と`managed-audit-results.json`へ保存する。監査の途中結果は開発用`build/managed-audit/`に保持する。別PC・WAN・ゲーム進行の検証結果とは分けて扱う。
