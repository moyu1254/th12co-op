# Phase 3：部屋番号の中継フォールバック

2026-11-16。通信 Protocol 7、協力 Rules 6、ローカル IPC 1。Windows 上の同一 PC にテスト用の HTTPS/WSS サーバーを起動し、二つのランチャーの通信処理を実行した。外部へのデプロイは行っていない。

| 条件 | 確認内容 |
|---|---|
| 直接 UDP が使える | ICE・QUIC で接続して照合後にレコードを往復。両側とも WSS 要求は0件。 |
| 片側の候補がない | ホストの IP 証明を取得できない条件で、同じ番号から双方が WSS に1回ずつ接続。ゲスト側だけの IP 証明が失敗する場合は下記の実ゲームで検査。 |
| 候補はあるが到達不能 | テスト用ディレクトリの応答で両側のポートを応答しないループバックソケットに置き換えた。実際の ICE チェックの後に WSS で照合し、4096 bytes のレコードと応答を交換。 |
| ICE は成功するが QUIC が通らない | 模擬 NAT の選定済み経路で QUIC Initial を破棄。ホスト・ゲストの両方が中継の対象となる到達性エラーを返すことを確認。 |
| 片側だけ直接経路が使える | クライアントの QUIC Finished が届かない場合も両者が到達性エラーを返す。別の結合試験では、直接 QUIC で認証を終えたゲストが経路の確定を待ち、ホストが到達失敗を報告すると、同じ部屋の中継で両者が再認証してレコードを交換した。 |
| ICE が登録外の IP を選定 | 選定した相手の IP が通知済みの候補に含まれない場合、その経路を拒否し、中継を選べることを確認。 |
| 接続確立前の取消 | ゲストの QUIC 証明書検証が失敗した場合、ゲスト側は認証エラーを返し、経路を照会中のホストは5秒以内に終了。WSS 要求は両側とも0件。ホスト応答待ちでの利用者の取消を模擬し、役割違いのトークン、取消の再送、成立済み中継への影響も検査。 |
| 参加認証・終了 | 直接 QUIC と中継内 TLS で、証明書や参加鍵が違えば検証する側で認証失敗。WSS で両者の照合コードが一致し、片側だけの承認では開始しない。送信直後に閉じても最後のレコードが届き、その後にストリームの終了を検出。 |
| 接続制限と解放 | 応答登録前・役割違い・二重接続・使い直しを拒否。実際の WSS ソケットで、断片を合算して16 KiBちょうどは通り、超過時はその一部も相手に渡らないことを確認。小さいペア数・転送量・期限を設定し、枠不足、双方向合算の上限、片側待ちと稼働中の失効、切断後の枠の再利用を検査。 |
| 部屋の期限・中継枠 | 公開期限をまたぐ参加・応答・中継予約と、再送で期限が延びないことを確認。実際の WSS で同じ IPv4 の3組を接続し、短い試験用期限で無通信・片方向だけの通信が枠を返し、双方向に通信中の組が継続することを検査。 |
| ゲームと独立した生存確認 | 中継の無通信期限を15秒に設定し、両端が照合を終えた後、暗号文を未読のまま18秒間アプリの読み書きを止めた。再開後に元の4096 bytesと逆方向の応答が順に届いた。片側だけが生存通知を送るペアは、無応答の端末を期限内に検出して枠を返した。 |
| 生存通知の互換性 | サブプロトコルを提示した端末だけが生存通知を使い、相手には通知に続く16 KiBのデータだけが届いた。サーバーがサブプロトコルを選択しない場合にもランチャーが照合・レコード交換・終了まで進んだ。 |
| 終了時の逆方向の配送 | 一方が Close を送った3秒後に、もう一方が送信中メッセージの最後の断片を送信。逆方向のメッセージ全体と両方向の Close が届いた。ランチャーでは受信待ちの有無と取消直後を検査。WSS 上の peer TLS でも、一方が終了した後、他方が1.5秒遅れて逆方向のレコードを送ってから、先に終了した側の最終レコードと EOF を受信した。 |
| 送信中の取消 | 1件の TLS 書き込みを複数の WebSocket メッセージに分け、最初の送信中にアプリ側を取り消した。受信側では残りの暗号文と Close が順に届き、送信待ちのまま取り消された書き込みは相手に届かなかった。 |
| 終了時に相手から応答が来ない | TLS の終了通知の書き込みを保留しても呼び出し元が戻ること、相手が最後の断片も Close 応答も送らない場合は40秒の期限で保留中の受信とソケットを解放することを確認。 |
| ランチャーの終了 | 2接続の終了通知を同時に保留し、プロセス終了時の待機が短い期限で戻ること、TLS から WSS に移る間も送信待ちが継続することを検査。両方の WSS Close が届くと、相手の応答を待たずに終了できた。 |

## 実ゲームと未検証範囲

通常版 1.00b の専用コピー2つを使い、各経路を60秒ずつ検査した。下表の確認フレームは試験終了時の値。過去の実行結果と使用バイナリは各時点の記録にある。[初回](https://github.com/moyu1254/th12co-op/blob/960b6806f0cfa213fb3c5fc13153e13643fb4dfe/verification/phase3-relay.md)・[レビュー1回目](https://github.com/moyu1254/th12co-op/blob/424a41a39e6a2efd6a62a70feeb26263abbce39b/verification/phase3-relay.md)・[レビュー2回目](https://github.com/moyu1254/th12co-op/blob/5d11536aa4c5499d2df79a7bedd7ca7ca0913974/verification/phase3-relay.md)

指定時間が満了して停止を指示した後に正規の終了レコード（`0x14`、理由1）が届いた場合は `peerGoodbyes` に記録する。途中終了や不正なレコード、他の I/O エラーは失敗として扱う。

| 経路 | ホストの確認フレーム | ゲストの確認フレーム | 中継要求（ホスト／ゲスト） | 通信エラー |
|---|---:|---:|---:|---:|
| 直接 QUIC（双方が認証完了を申告） | 3,298 | 3,299 | 0／0 | 0 |
| WSS 中継（ゲストの IP 証明を取得できない条件） | 3,383 | 3,383 | 1／1 | 0 |

両試験ともホスト・ゲストがステージに到達し、各プロセスの非表示・無音と終了を確認した。直接では両者とも3,300フレームまでコミットし、停止時の相手との照合済みフレームには1フレーム差があった。中継では停止時にゲストがホストの正規の終了レコードを受信した。

| 接続環境 | 2026-11-16 の Phase 3 実装時点の判定 |
|---|---|
| 同一 PC、IPv4 ループバック、通常版 1.00b 同士 | 直接 QUIC と WSS 中継で接続可。 |
| 別 PC・同一 LAN、実機の UPnP | 未検証。 |
| 別 PC・別回線：フルコーン／制限／ポート制限／シンメトリック NAT の各組み合わせ × IPv6 有無 × UPnP 可否 | すべて未検証。模擬環境での直接接続失敗や中継成功から、個別の WAN 環境の成否は判定していない。 |

通常版 1.00a・Steam 版での中継、全ステージ、通話での人手照合、公開サービスの運用・負荷・費用はこの Phase 3 試験の対象外。後続の [v0.4.0-rc.1 の試験](releases/v0.4.0-rc.1.md)で Steam 版 1.00b 同士の直接 QUIC・WSS 中継を同一 PC で確認した。

Windows 11 Home（build 26200）、.NET SDK 10.0.403。自己完結版のビルド、ランチャー自己テスト23グループ（内部の managed 回帰19グループを含む）、ネイティブ診断ビルド、配布処理の合成テスト6件も合格した。

## 別 PC での検証手順と記録欄

1. Windows 11 の2台に同じ Protocol 7 の配布候補を展開し、各自の対応版の原作を用意する。試験日、コミット、両端で照合した ZIP の SHA-256、両端の原作の版と `th12.exe` の SHA-256、稼働中の `TH12Coop.Rendezvous.dll` の SHA-256 を記録する。指紋は `Get-FileHash -Algorithm SHA256` で取得できる。
2. 両端で同じ合流サーバーを設定する。両回線から同じホスト名へ HTTPS/WSS と STUN（UDP 3478）で接続できるようにする。[運用手順](../docs/rendezvous.md)
3. 最初に別 PC・同一 LAN で部屋を作成し、ゲストが6桁を入力する。ホスト側の実ルーターで、開始前・接続中・終了後の UDP 転送一覧を比較する。今回のホスト宛ての転送が追加されたか、直接接続の終了時または中継への切替時に解放されたかを個別に記録する。ルーターで確認できない項目には「不明」と記入する。
4. 両端で照合画面の接続経路を確認し、コードを通話などで読み合わせる。一致した場合だけ双方で承認する。両者がステージに入り、双方の入力で自機が動くことを確かめる。継続時間を測り、途中切断やエラーがあれば発生段階を記録する。
5. ゲストを別回線に移し、新しい部屋番号で繰り返す。回線条件やホスト役を変えたら1行追加する。

| 試験日・環境 | ホストの IPv4 NAT／IPv6 の有無／UPnP 可否 | ゲストの IPv4 NAT／IPv6 の有無／UPnP 可否 | ホストの UDP 転送（追加／解放） | 実際の IP バージョン（ホスト／ゲスト） | 判定・観測結果 |
|---|---|---|---|---|---|
| 別 PC・同一 LAN | — | — | — | — | 未検証 |
| 別 PC・別回線 | — | — | — | — | 未検証 |

IPv4 NAT はフルコーン／制限／ポート制限／シンメトリック／NAT なしのいずれかを、確認方法とともに記す。確かめられなければ「不明」とする。IPv6 が利用できても IPv4 でつながる場合があるため、実際の IP バージョンは直接 QUIC の相手向け通信、または各端末からサーバーへの WSS 通信で確認できた場合だけ記入する。

両者が照合とゲーム開始を確認できたら、照合画面の経路に従って「直接 QUIC で成功」または「WSS 中継で成功」とし、継続時間を添える。ゲーム開始まで進めなかった場合は「接続失敗」とし、最後に到達した段階とエラーの要旨を書く。未実施の組み合わせは「未検証」のままにする。公開する記録には部屋番号、照合コード、招待・トークン、IP アドレスを含めない。

```powershell
.\build.ps1 -SelfContained
```
